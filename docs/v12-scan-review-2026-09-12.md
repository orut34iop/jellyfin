| 优先级 | 问题及证据 | 修复 |
| --- | --- | --- |
| P1 | `GetPerson` 使用 `BaseItems.Type + lower(Name)` 查找人物；旧索引只筛选 Type，需要逐条检查约 14 万个人物。实际 EF 命令多次耗时 592–865 ms。之前只优化 `Peoples` 表没有覆盖这条路径。 | 正式数据库迁移增加 `IX_BaseItems_Type_NameLower`；回归测试检查 EF 实际生成 SQL 的执行计划。 |
| P1 | 原生 `opendir` 失败被当成空目录，`readdir` 也未区分错误与正常结束；目录枚举中途失败可能落到删除旧条目的逻辑。 | 读取失败抛出 I/O 异常；Folder 在调整数据库前完整枚举，失败时保留已有条目。覆盖开始及中途失败。 |

| P2 | 人物映射快速路径的角色比较与实际写入语义不一致，大小写差异会反复进入写事务；事务外加载的 tracked 数据可能在并发更新后过期。 | 按既有大小写不敏感规则比较；快速路径不跟踪实体，需要更新时在事务内重读映射。 |
| P2 | 本地模式一概跳过提取数据清理，范围大于需要避免符号链接占位时间戳误判的场景。 | 仅在使用视频占位元数据时跳过清理；`.strm` 等仍使用真实文件信息的路径继续按真实变更清理。 |

## 解释边界与后续观察

此前“8 分钟到 96%”出现在取消相关流程中，不能作为优化成功或真实完成的证据。
本次明确撤回该性能结论。应以未取消的扫描完成记录和实际条目变化核验最终结果。

扫描百分比仍是层级阶段加权进度，不是影片数的线性百分比，不能直接用于估算剩余天数。
本次进度修复覆盖扫描报告和日志；通用 ScheduledTaskWorker 仍通过异步 Progress 事件
向外传递更新，未将此次变更扩大为所有计划任务的事件机制重构。

本地导入模式限制扫描的远端元数据和视频探测行为，并不等于整个进程禁止网络。
启动日志有独立的插件更新任务；恢复扫描后的连接快照也存在一个非回环 HTTPS
连接。该快照不能确认连接的请求用途，更不能证明整个导入期间从未访问网络。

目录、NFO、图片与 SQLite 的必要 I/O 仍存在。后续若出现持续停滞，应结合当前
阶段、具体查询和线程采样定位，避免仅凭进度平台期反复重启扫描。
