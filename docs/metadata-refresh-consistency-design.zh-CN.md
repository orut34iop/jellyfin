# 媒体信息读取与元数据刷新一致性方案

日期：2026-10-19（Asia/Shanghai）

状态：最终设计基线，已有本地实现；验证结果和剩余范围见文末，上游评审尚未进行。本文定义目标行为，不表示这些行为已经全部实现或被上游接受。

英文版本：[Metadata Read and Refresh Consistency Design](metadata-refresh-consistency-design.md)。后续向上游提交英文版本，中文版本保留供本地审阅。

## 目标与适用范围

媒体信息读取应优先使用数据库中对当前媒体源有效的数据。只有当前操作需要的信息尚未获取或已失效时，才进行针对性的补充。补充技术信息、扫描媒体库和导入描述信息必须有清晰边界，避免播放、字幕维护或后台刷新意外覆盖用户已经整理的字段。

本方案覆盖电影、电视剧、季、单集，以及关联的多版本和分段视频。核心规则适用于普通文件、符号链接和 STRM；本地极速导入仅是一个典型场景，不是上游修复的依赖条件。其他媒体类型和插件需要经过对应测试后才能声明具有相同保证。

典型流程是：从 NFO 导入影片，不预先探测视频；外部工具通过 API 翻译、归并流派和地区；将同一影片关联为多版本；随后正常播放、扫描和维护。整理结果必须在其明确的保护范围内持续有效。

不在本次范围内：内置翻译服务、按标题自动判断电影相同、全媒体元数据来源历史系统、默认重写用户 NFO、数据库删除后的无备份恢复、媒体文件写入以及整个 API 的重新设计。

## 当前事实与设计边界

上游核对基线为 `08c2ba6e0b6499122822f1c5b18bc426104538b4`。本地代码引用固定于定制分支提交 `d49bd1bb15467d59f0a09240a629fe5abe255909`，用于区分本地扩展与上游行为。以下是代码或上游讨论确认的事实，而非目标行为：

- 播放 STRM 或缺少主要音视频流的条目时，`MediaSourceManager.GetPlaybackMediaSources` 会请求 `FullRefresh`。它没有将播放探测与描述信息刷新分离。[播放入口](https://github.com/jellyfin/jellyfin/blob/08c2ba6e0b6499122822f1c5b18bc426104538b4/Emby.Server.Implementations/Library/MediaSourceManager.cs#L182-L194)
- 本地元数据合并存在锁定 NFO 的覆盖分支；地区字段在非替换合并时也可能追加来源中的地区。因此 `ReplaceAllMetadata=false` 不等价于“所有已有值保持不变”。[合并分支](https://github.com/jellyfin/jellyfin/blob/08c2ba6e0b6499122822f1c5b18bc426104538b4/MediaBrowser.Providers/Manager/MetadataService.cs#L908-L917)、[地区合并](https://github.com/jellyfin/jellyfin/blob/08c2ba6e0b6499122822f1c5b18bc426104538b4/MediaBrowser.Providers/Manager/MetadataService.cs#L1295-L1304)
- Jellyfin 已有字段锁 `LockedFields` 和整体锁 `IsLocked`，NFO 分别使用 `lockedfields` 和 `lockdata`。字段锁是字段列表，不是“锁定 NFO 中所有出现的字段”的布尔开关。[NFO 文档](https://jellyfin.org/docs/general/server/metadata/nfo/)
- 当前元数据编辑 API 可以直接修改流派、地区；锁定不等于拒绝所有人工 API 编辑。[编辑入口](https://github.com/orut34iop/jellyfin/blob/d49bd1bb15467d59f0a09240a629fe5abe255909/Jellyfin.Api/Controllers/ItemUpdateController.cs)
- 本地 `BaseItem.RefreshMetadata` 在进入元数据服务前会处理附属条目和图片；多版本条目还存在递归维护路径。因此只在提供者合并阶段增加保护不够。[刷新入口](https://github.com/orut34iop/jellyfin/blob/d49bd1bb15467d59f0a09240a629fe5abe255909/MediaBrowser.Controller/Entities/BaseItem.cs)、[版本维护](https://github.com/orut34iop/jellyfin/blob/d49bd1bb15467d59f0a09240a629fe5abe255909/MediaBrowser.Controller/Entities/Video.cs)
- 本地极速模式限制目标视频访问和远程获取，不意味着禁止以后读取 NFO。多版本合并保留各版本独立条目，并不自动统一各版本的流派和地区。[极速模式](https://github.com/orut34iop/jellyfin/blob/d49bd1bb15467d59f0a09240a629fe5abe255909/MediaBrowser.Controller/Library/LocalMetadataOnlyImportPolicy.cs)、[版本合并](https://github.com/orut34iop/jellyfin/blob/d49bd1bb15467d59f0a09240a629fe5abe255909/Jellyfin.Api/Controllers/VideosController.cs)

这些事实证明存在覆盖风险，但不能代替对某个实际条目覆盖来源的复现。实现前须建立包含 API 修改、NFO、锁状态及播放请求的最小复现。

### 实现阶段的复现步骤

以下是待执行的验证流程，不表示已经在所核对的上游提交上完成运行时复现。

1. 记录服务器提交或版本、客户端、启用的元数据提供者和保存器、媒体库配置及锁状态。使用独立测试库、小型合法测试视频及对应 NFO，给流派和地区设置容易辨认的原值。隔离播放测试时暂停无关定时任务，之后再单独验证这些流程。
2. 分别测试普通文件与 STRM。已核对的上游 STRM 分支可触发刷新，不依赖本地极速模式。缺失流信息的场景应采用受控测试夹具或支持的导入流程，并说明缺失状态如何产生；不能宣称普通文件的常规导入天然不做探测。
3. 通过元数据编辑 API 将流派和地区改成不同的整理值，同时保留接口要求的 DTO 字段。读回并保存值和锁状态。测试旧 NFO 覆盖时关闭 NFO 保存，并确认 NFO 仍是原值。
4. 请求播放信息并播放条目。记录条目和所选媒体源标识、前后技术信息、刷新及提供者日志、描述字段、锁和版本关系。失败基线必须证明数据库已提交值被改变，不能只凭客户端缓存显示旧文本判定。
5. 加入明确字段锁、受保护的空地区及多版本后重复测试。分别执行补全、替换全部刷新、扫描和字幕维护。逐项记录哪个触发器造成变化，不因症状相似就认定根因相同。
6. 实现后用相同夹具运行下文验收矩阵，包括冷启动及并发 API 编辑。上游复现材料不得包含私人媒体路径或凭据。

## 核心规则

| 编号 | 必须满足的行为 |
| --- | --- |
| R1 | 普通读取和播放优先使用数据库当前已提交、有效的数据，不因读取本身重新导入描述信息。 |
| R2 | 当前操作只补充它所必需且缺失或失效的信息；缺少简介不是播放探测的理由。 |
| R3 | 为补充技术信息而运行的提供者，不得写回流派、地区、标题、简介等描述字段，即使探测结果同时包含这些字段。 |
| R4 | 受保护描述字段不得被自动来源替换、追加或清空，明确保护的空值也有效。 |
| R5 | 有编辑权限的用户或工具可以明确修改受保护字段；修改值不自动解除保护。 |
| R6 | 普通扫描和“替换全部元数据”均尊重字段锁；解除保护或重置保护字段必须表达明确意图。 |
| R7 | 旧刷新任务不能覆盖其开始后成功保存的人工编辑、锁状态或版本关系。 |
| R8 | 描述信息刷新和技术探测不能隐式拆分、重建或重新选择人工建立的版本组。 |
| R9 | 文件访问失败、网络故障和探测失败不等价于媒体删除或已有数据失效。 |

“数据库最新”指当前已提交的有效状态，包括正确失效或同步的内存缓存；不表示比较数据库时间与 NFO 文件修改时间后让较晚者获胜。

技术信息包括当前操作所需的时长、容器、编码、分辨率、音视频及字幕流、章节。技术探测不得用视频内嵌标签填充描述字段，即使描述字段为空。简介、评分、演职人员、标签及提供者标识继续遵守各自的元数据或明确身份编辑范围；图片使用独立刷新范围。章节、缩略图、trickplay 等技术维护任务若调用公共刷新路径，也须遵守上述边界；这是目标约束，不表示这些任务目前全部会重新导入 NFO。这些操作不得在正常、独立授权的播放状态更新之外改动用户播放记录或收藏。

## 信息状态与按需补充

| 状态 | 示例 | 行为 |
| --- | --- | --- |
| 已知且有效 | 当前媒体源的编码；API 保存的“剧情” | 直接使用。 |
| 明确保留为空 | 用户清空地区并保护该字段 | 返回空值，不按缺失处理。 |
| 尚未获取 | 极速导入后没有视频流信息 | 当前操作确有需要时获取。 |
| 已确认失效 | 已确认源文件替换或 STRM 目标改变 | 使相关技术数据失效，按需重新获取；保留描述字段和版本组。 |
| 获取失败或暂不可用 | NAS 离线、探测超时 | 保留已提交数据，返回适当错误或可用结果；允许有界重试。 |

空值、零值和占位值不能统一判断。例如零时长可能无效，零播放次数则有效；NFO 时长可能足够展示，但不一定足以证明当前流适合转码。有效性应按字段和用途判断。

先复用已有字段锁表示“明确保留的描述值，包括空值”，复用已有媒体源标识、文件变化证据和流信息。只有确有无法表达的状态时，才提出最小的数据模型扩展；不以本方案为由引入全字段来源账本。

有效性检查不得导致每次读取都访问符号链接目标。占位文件时间或大小不能作为真实视频变化证据。对无法可靠判断是否变化的远程源，必须保留按需复查、明确强制探测或具体播放错误触发的有界恢复途径，不能因数据库已有一个流记录而永久禁止复查。

技术信息写回范围以媒体源为单位。获取到同一源的完整音视频流信息时，可以原子更新相关流、时长和容器信息；不要求机械地每次只写一个缺失字段。只在成功验证新结果后替换相关旧结果，取消或失败不能先清空现有数据。

## 字段保护与编辑契约

优先复用 `LockedFields`，首先完整覆盖 `Genres` 和 `ProductionLocations`，并为本次涉及的其他受支持描述字段验证一致性。保留整体锁已有用途，不把 NFO 锁解释为 API 权限限制，也不依据某个 XML 标签是否出现就自动创建编辑禁令。

外部整理工具在保存中文化结果时，应在同一次逻辑更新中保存字段值与保护状态，并保留其他已有锁。需要持续保护的空值也采用同样规则。API 写入本身不自动证明该字段应永久优先于来源：调用方必须明确请求保护。这个规则避免完整 DTO 提交把所有未编辑字段意外锁住。

对于单个条目，服务器必须原子保存选定字段值及所请求的保护状态，并防止并发刷新提交绕过此保证。一次 HTTP 请求本身不等于已经具备原子性，依赖前须验证现有持久化路径。跨条目的批量更新应显示进度并可恢复执行，不宣称整个媒体库一次事务完成。导入 NFO 锁标志不能静默解除数据库已有保护，也不能授权覆盖受保护值。

| 编辑意图 | 值和保护状态 |
| --- | --- |
| 修改并保护流派 | 保存新流派，增加流派锁，保留其他锁。 |
| 再次修改已保护地区 | 保存新地区，地区锁继续存在。 |
| 清空并保护地区 | 保存空集合，地区锁继续存在。 |
| 未提交某字段的更新 | 不推断为清空，也不推断为解除保护；已有接口的具体语义须单独核对。 |
| 明确解除字段保护 | 只解除指定字段，其他锁保持不变。 |
| 普通完整元数据刷新 | 允许更新未保护字段，保护字段保留。 |
| 明确从来源重置保护字段 | 仅作用于选定字段和条目；来源获取成功后才提交，不隐式改变其他字段。 |

现有完整 DTO 更新接口不是可直接当作 PATCH 使用的接口。集成工具应遵守当前契约，保留必要字段及已有锁；本方案不提供可直接执行的稀疏 DTO 请求示例。不在修复播放的 PR 中悄悄改变所有客户端的更新语义。

保护字段重置属于单独的编辑意图，不能用短暂解锁、排队刷新、再锁回的异步组合实现。若现有 API 无法原子表达，另行讨论增量接口或显式选项。重置成功后默认保留原保护状态；解除保护是另一项明确操作。来源失败时保留旧值和旧锁。

技术有效性与描述字段锁分开处理。媒体探测器可以发现真实运行时信息，但不能通过技术探测顺带填充受保护描述字段。对 `Runtime` 等已有锁枚举与探测结果的交互，须单独验证现有语义，不借本方案泛化改变所有技术字段锁。

## 各类刷新场景

| 场景 | 允许的获取和更新 | 必须保留 |
| --- | --- | --- |
| 新条目首次导入 | 按库配置导入 NFO、图片及允许的来源；普通库按原规则探测 | 已有匹配条目的人工保护，不能把它误判成全新记录。 |
| 极速模式首次导入 | 解析本地 NFO 和允许的本地资源，不访问视频目标 | 目标文件不被预先探测；占位信息不冒充真实技术信息。 |
| 普通详情和列表读取 | 读取数据库；既有特定实体的按需刷新须独立评估 | 不对电影、剧集隐式触发描述信息重导入。 |
| 首次播放且流信息不足 | 获取当前源需要的技术信息 | 所有已有描述信息、字段锁及版本组。 |
| 重复播放且信息有效 | 直接使用已有流信息 | 不重复全量刷新或仅因扩展名为 STRM 就重新探测。 |
| 源变化或技术数据失效 | 针对变化源重新验证和探测 | 人工描述信息和其他版本的有效技术信息。 |
| 字幕添加、下载、上传或删除 | 使用当前目录状态更新字幕发现和相关流信息 | 描述字段；不得用旧目录缓存恢复已删除字幕或丢弃新增字幕。 |
| 明确只刷新图片 | 在请求的图片范围内发现或替换图片 | 描述值、锁、流信息和版本关系；图片刷新不授权重新导入描述信息。 |
| 手动或定时媒体库扫描 | 发现新增条目，检查变化，按原配置刷新未保护字段 | 所有受保护值，包括空值及已有版本关联。 |
| 文件变化监听 | 识别变化类型并执行必要更新；无法细分时仍应用统一保护 | 不能因为字幕或图片变化就覆盖保护字段。 |
| 自动刷新周期到期 | 正常刷新允许的来源和未保护字段 | 锁定字段；技术探测不能冒充一次成功的描述信息刷新。 |
| 查找缺失元数据 | 按来源规则补充真正未知的描述字段 | 已知值和受保护空值；不得借补全追加旧地区。 |
| 替换全部元数据 | 替换未保护字段，按配置刷新图片 | 锁定字段和人工版本关联。 |
| 识别影片或修改剧集显示顺序 | 执行明确身份或排序变更及所需递归刷新 | 保护字段；身份变更不自动授权拆组或解除保护。 |
| 附属视频、分段和父子继承 | 仅在明确需要时维护相应信息，检查目标字段锁 | 子项独立保护值；技术请求不得扩散成无关描述刷新。 |
| 合并、拆分或选择主版本 | 通过明确的版本管理操作修改关系 | 未请求修改的描述字段、用户播放数据和每个源的技术信息。 |
| 插件请求标准刷新 | 遵守同一刷新范围和字段保护 | 不能绕过统一策略。直接写数据库的插件不在此保证内。 |
| 删除后重新导入或重建数据库 | 使用备份或整理结果清单显式恢复 | 不宣称已经删除的锁和人工关系能够自动复原。 |

极速模式目前跳过部分后台工作，例如自动字幕下载。这属于本地兼容性验证；上游核心规则不能依赖这些任务被禁用。演员按需刷新、流派实体校验和其他聚合实体维护不能自动等同于影片字段刷新，需要按受影响实体分别测试。

## 多版本和分段保护

版本组共享的是明确的关联关系；每个媒体源仍有独立的编码、时长、音轨、字幕和路径。获取某一版本的技术信息不能覆盖另一版本，也不能因为新探测到了更高分辨率就隐式改变人工选定的主版本。

现有组内条目继续保留独立的描述字段。服务器不默认把所有成员的标题、简介或地区同步为同一份。外部工具可以在确认组成员身份后，将选定的公共字段及锁应用到明确的成员列表；这是整理操作，不是每次扫描的隐含行为。

合并前须处理冲突：成员流派或地区不同不能随机取最后一条、自动求并集或仅凭电影标题相同就覆盖。工具先确定最终值，再更新选定成员和保护状态，最后建立或确认关联。操作需要能检查中断后的部分完成状态，并可幂等重试；现有多个 HTTP 请求不被宣称为一个数据库事务。

新加入的版本先按普通新条目导入，不静默覆盖组内已有整理结果，也不默认继承锁。将新版本纳入整理范围是明确操作。拆分后各成员保留自身值和锁。某个成员暂不可访问不代表应拆组；确认删除仍按既有删除流程处理，不能借“保护”无限保留已明确删除的记录。

本地扫描器创建的版本、API 人工合并的版本和分段视频必须分别验证。它们有不同维护路径，不能用其中一种通过测试替代其他两种。

## 实现约束和并发

统一决策应同时覆盖刷新入口、提供者写回、父子继承、数据库保存和缓存失效。具体类型名和参数不是本设计预先规定的新 API。

建议执行顺序：读取当前条目与目标媒体源；确定操作需要的信息及其有效性；选择最小获取范围；在临时结果中执行必要获取；提交前检查当前值、锁状态和媒体源是否发生变化；只提交本次范围允许的字段；使相应缓存失效或同步。

长时间网络或 ffprobe 工作不应占用数据库写事务。并发控制可采用已有的条目协调机制或乐观版本校验，但必须证明：较早启动的刷新不能覆盖较晚提交的人工编辑；旧源的探测结果不能写入新源；相同源的重复请求不会无界重复探测。冲突后应重新读取并重新判定或放弃过期结果。

播放探测不得更新“描述信息已完整刷新”的时间戳。若需要记录探测新鲜度，使用适当的独立状态。技术探测失败必须仍可重试，同时避免每个请求无限重试。日志至少区分读取、探测、描述刷新、保护跳过和明确重置，且不得记录访问令牌或带凭据的远程地址。

最初实现应复用现有存储和字段锁。若评审发现无法可靠表达必要的技术状态，再以独立、向后兼容的迁移补足；不提前规定一套新的通用元数据数据库。

## 已有媒体库接入与恢复

启用前备份数据库及人工版本关联，导出需要保护的当前字段值。不能从“含中文”或“非空”自动推断已被人工整理。由工具的处理结果或用户选定范围明确决定保护对象。

对已正确整理的条目写入相应锁，不重新读取 NFO 来初始化保护值。已经回退的数据须由备份、整理清单或重新执行翻译恢复，修复代码不能推导被覆盖的原值。后续工具每次修改时保存值与锁，并覆盖明确选定的所有版本成员。

NFO 写回维持库现有配置，本修复不默认开启 NFO 保存，也不改变极速模式的文件写入策略。若已开启保存，输出应反映已提交的受保护值；写入失败应报告，不能用旧 NFO 反向覆盖成功保存的编辑。

重新创建条目后的恢复不能只依赖旧 ItemId，也不能只凭标题或单一外部 ID 自动匹配。需要库范围、逻辑路径、媒体类型和版本成员等足够证据，存在歧义时留待人工确认。

需要显式重新验证时，有权限的管理员可调用 `POST /Items/{itemId}/Refresh?refreshMediaInfoOnly=true`。此请求为视频或音频条目排队；HTTP 204 仅表示已排队，不代表探测成功。与图片、trickplay 或元数据替换选项冲突时返回 HTTP 400。该选项默认关闭，已有请求的 API 契约保持不变。它与重置受保护描述字段相互独立，不解除任何字段锁。

普通播放不会为判断新鲜度而在每次读取时访问符号链接目标或 STRM 文件。源变化由已有扫描、监听刷新路径或明确重新验证请求发现。视频刷新中的 `FileExists` 失败不再删除附属视频或裁剪本地版本列表；删除交由成功的媒体库协调流程或明确删除操作处理。

技术信息持久化即使收到旧条目实例，也会保留数据库已提交的描述字段和版本数据。流、附件、章节仍使用现有仓储，尚未组成跨所有技术表的一次事务。当前实现会在写入前拒绝无效或过期探测结果，字幕维护保留附件与章节，但不宣称具有跨仓储的崩溃原子性。

技术信息持久化后使条目及父级缓存失效，并发送既有条目更新事件。刷新和附属条目继承取得锁后重新读取当前条目；文件夹锁传播也重新读取每个目标。

异步锁是进程内协调，不是在网络访问期间持有数据库事务；它也覆盖附属条目继承写入及现有的文件夹锁传播，但不能因此宣称绕过标准入口的插件也受保护。保护字段显式重置、完整失败原子性、媒体库恢复及完整验收矩阵仍需分别实现或验证，不能从播放修复推断它们已完成。
