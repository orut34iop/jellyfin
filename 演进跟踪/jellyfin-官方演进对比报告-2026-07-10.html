五、升级风险判断

1. 12.x 不是普通补丁升级

官方 RC2 明确说明：首次启动会执行数分钟迁移；升级前需在 10.10.7+ 或 10.11.x；外部插件可能无法直接工作，应停用并改用官方 unstable 插件仓库。对当前 Folk 而言，还要增加“数据库备份可恢复、启动迁移可中断/重试、插件重新安装、Moonfin 直播放可用”四项门禁。

2. 多版本媒体会触碰播放状态与客户端假设

官方把播放进度、Resume、Continue Watching、Next Up 和 extras 都改成 version-aware。Moonfin 当前依赖 Protocol = File 加本地绝对路径直播放，必须验证媒体源选择、版本分组、播放进度回写和备用版本切换是否仍然满足客户端预期。

3. Folk 的库/数据库改动与官方性能改动可能相互作用

Folk 已修改 DTO、PeopleRepository、扫描策略和 SQLite 锁；官方也在扫描调度、查询投影、批量删除和库查询上持续改造。建议按功能切片重放，而不是把 master 与 Folk 分支做一次大 rebase 后凭编译通过即上线。

4. 不能把官方 master 当作稳定目标

截至报告日官方最新公开预览是 12.0-rc2，master 仍在继续变动。master 的新增提交适合作为候选修复池，不适合作为生产升级基线。生产决策应等待 12.x 稳定版，或只回移明确、局部、可测试的修复。

七、推荐迁移路线

  1. 冻结现状：为当前 Folk HEAD 做完整数据库、插件、配置和媒体路径备份，记录 Moonfin 的 directPlay 与 isLocalFilePath 诊断。
  2. 先做 10.11 系增量：优先归并 P0/P1 的局部修复；每批只改变一个主题，并保留 Folk 现有测试。
  3. 建立 12.x 迁移分支：以官方 12.0 RC2/后续稳定版为基线，先跑迁移与插件矩阵，再迁移 Moonfin、local-metadata-only 和 SQLite 锁策略。
  4. 做数据和播放回归：重点覆盖大库扫描、备份、恢复、符号链接、多个版本、字幕、Live TV、SyncPlay、普通客户端及 Moonfin。
  5. 上线门禁：只有当迁移可恢复、API 卡顿指标不恶化、Moonfin 仍然直放、插件可用且无数据丢失时，才从测试预览转生产。
